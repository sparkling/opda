# Operational trust and what the property sandbox can teach

For implementers, data providers, property professionals and programme participants.

An agreed meaning is necessary for useful data sharing, but it does not establish a working connection. A provider still needs to know which organisation and application are asking for information, whether they are permitted to connect and how an exchange will be recorded. The property trust-framework sandbox explores those operating questions in a controlled environment. Its lessons complement the Property Pack's semantic work; they do not establish that the draft ontology has been adopted or that a production scheme exists.

Three retained sources offer different views of this work. The technical guide explains how participants register APIs and applications and establish protected communication. The DPMSG trust-framework explainer describes the proposed operating model. OPDA's *Building Trust in Property Data* article reports a first sandbox test involving HM Land Registry, Kotini and Raidiam. Reading these together connects procedures, intentions and reported experience without treating them as the same kind of evidence.

## The roles behind an exchange

The technical guide distinguishes a Data Provider, which exposes information through APIs, from a Data Receiver, which consumes another organisation's APIs. An organisation can hold both roles. These are roles in the sandbox's operating arrangement, not permanent classifications of everything an organisation is or does.

A provider registers an authorisation server and its APIs. This makes an authorised endpoint discoverable and establishes how access is managed. A receiver registers an application, also described as a software statement, with information about the software, its permitted roles and associated certificates. The provider can then associate a connecting application with an authorised participant. Organisation, software and individual user are distinct subjects: identifying one does not automatically identify or authorise all the others.

The guide describes an OAuth2.0-compliant authorisation server and an mTLS gateway among provider prerequisites. The former manages access to APIs; the latter supports verified connections. It also describes a managed authorisation-server option. These are concrete elements of the retained sandbox design, not a universal prescription that every future Property Pack implementation must purchase or deploy the same components.

## An illustrative request through the system

Suppose a receiving application requests a property record from a registered provider. The directory and registration arrangements help it discover the provider and present its application identity. The provider's operating controls determine whether the connection and request are permitted. An exchange can then be recorded with enough context to investigate what was requested and supplied.

Several questions remain after the connection succeeds. Does the response concern the intended property? Which source supplied each statement? Was a value current at the relevant time? Does the recipient have enough context to use it for the proposed task? The semantic model, provenance and use-specific rules help answer these questions. A successful authenticated request demonstrates a transport and participation relationship; it does not certify every assertion in the response as true or sufficient for legal or lending judgement.

The DPMSG explainer gives a helpful property example: an approved extension or energy certificate may be supplied by an authenticated provider, with source, timestamp, version and provenance information. Retaining those features allows another participant to understand what is being reused. Stripping them away and circulating only a value weakens the benefit of the trusted route.

## What the reported first test established

The retained *Building Trust in Property Data* article describes HM Land Registry as an authenticated primary data source, Kotini as an accredited recipient, and Raidiam as providing the sandbox infrastructure. It reports testing authenticated access, permissions and auditability. The article presents this as a foundational step towards how property information could be accessed in future, rather than as a completed transformation of the market.

This is an OPDA account of the test. It is useful evidence of the participants, intended mechanism and reported learning. It is not an independent performance benchmark, a complete security assessment or evidence that every future participant is compliant. The account also does not prove that the current machine-proposed Property Pack ontology was the payload or governed meaning used in that test.

That distinction makes the example more useful. Teams can identify the specific proposition tested—controlled exchange among recognised participants—and the propositions still requiring evidence. They need not choose between dismissing the pilot and claiming that one exchange proves an entire scheme ready.

## Why a sandbox is valuable

The technical guide explicitly calls this a pilot in a safe, non-production environment. It welcomes organisations with differing levels of technical readiness. This allows the programme to discover practical obstacles: a provider may need help registering an endpoint; a receiver may misunderstand application roles; a certificate or authorisation configuration may prevent an otherwise valid request.

Failures can reveal where responsibilities and documentation are unclear. For example, an application could be registered successfully while the requested API remains unavailable. Alternatively, access may work while the returned information lacks a property identifier or useful source date. Those are different failures with different owners. Treating every problem as “interoperability” would make it harder to decide whether the repair belongs in operational configuration, payload structure, semantic meaning or the participation rules.

A useful experiment therefore states its boundary. One exercise might demonstrate discovery and authenticated access. Another could demonstrate that the recipient can interpret a particular record without manual reconstruction. A third might examine correction, withdrawal or a changed permission. The latter examples are possible follow-on experiments, not claims that the retained first test completed them.

## From pilot learning to an operating scheme

Production use introduces questions that a successful demonstration does not settle: who maintains participant status, how access is removed, how incidents are handled, who answers a complaint and which obligations apply when supplied data is inaccurate. The retained MHCLG roadmap discusses future work on liability, consumer protection and secure sharing. Its proposals reinforce why technical success and institutional arrangements must develop together.

The DPMSG explainer similarly describes a rulebook covering who can participate, what can be shared and under which conditions. The rulebook, technical controls and data meanings serve different purposes. A policy expression does not enforce itself. A certificate does not define a property concept. A well-defined record does not make a recipient eligible to obtain it.

For an implementer, the productive hand-off is a precise claim with supporting evidence: these participants, using these arrangements, exchanged this kind of information under these conditions. For the model's domain owners, the next question is what the exchange revealed about the information people needed to interpret. That feedback can strengthen definitions and requirements while preserving the distinction between an operating pilot, a proposed scheme and the draft semantic candidate.
