# Contributing evidence and making a useful model review

For property practitioners, source owners and working-group reviewers.

A useful contribution connects a practical question to inspectable evidence. A mortgage dictionary, conveyancing form or example exchange can reveal a distinction that a proposed model has missed. It does not automatically establish a rule for every property transaction. The reviewer needs to understand who produced the material, which version applies, the context it describes and what the contributor is authorised to share.

The current participant guide separates source submission from discussion and from standards decisions. Accepted ADR-0070 establishes an organisation-isolated SharePoint intake boundary. Proposed ADR-0092, dated 11 October 2026, addresses participation when corporate restrictions prevent Microsoft tenant access. It records a real need and existing email contributions, while explicitly leaving tenant-independent website access to be verified. An invitation, receipt, upload, review and incorporation into a model are different events.

## Give the evidence enough context to be understood

Imagine that an organisation contributes a dictionary containing a field called `status`. Its definition alone might be too short to identify the subject. Is it the status of a mortgage application, a valuation instruction, a property listing or a particular verification? A source note should name the business context and the record containing that field. The same word can legitimately represent different concepts in different contexts.

The participant guide asks contributors to include an index or README identifying the source owner, version or date, applicability and intended contribution. It also asks whether the source is authoritative, informative, illustrative or disputed, together with relevant rights and handling restrictions. These descriptions help a reviewer weigh evidence; an organisation calling its own procedure authoritative does not make it a cross-industry rule.

Complete original files are preferable to isolated screenshots or unexplained field lists when permission allows. A schema's definitions, references and conditional branches can change the meaning of one visible field. A blank form's surrounding questions may explain when an answer is required. A dictionary may distinguish a source-system code from the business concept that the code represents. Keeping the original alongside the interpretation lets someone later challenge an incorrect extraction.

Useful material includes authorised standards and interface definitions, dictionaries, database structures, semantic models, blank forms, policies and fictional or properly anonymised scenarios. An example that fails a rule can be as valuable as one that passes. A transcript can preserve a domain explanation when recording upload is inappropriate. The current intake guide does not accept audio or video as source attachments; it directs contributors towards permitted transcripts.

## Keep the submission boundary clear

The working group's ordinary Team documents area is shared with the group. It is different from the separate source-intake site, where approved company contributors can access their organisation's area. Putting an organisation's source in a general discussion attachment can therefore cross a different visibility boundary from uploading it to the intended intake folder.

Contributors should use material they are authorised to share and omit live customer or transaction records, credentials and restricted material. An organisation's approved identity and access determine the appropriate route. A generic personal-email domain is not a reason to create one shared organisation folder for everyone using that provider. The current guide offers assistance and a screened email fallback rather than treating a blocked upload as evidence that the person has nothing useful to contribute.

ADR-0092 provides a helpful example of careful reporting: correspondence records receipt of a mortgage dictionary and a later fictional JSON example. It does not independently establish the spreadsheet's contents, its current storage location or its incorporation into the model. The fictional example's permission to share also does not imply permission to publish every item from the same contributor. Progress reporting should retain those distinctions.

## Review meaning before representation

A practitioner can review the model without editing RDF. Start with the proposed definition and ask whether a colleague would recognise the concept in a real case. Check what the relationship connects, in which direction, and under what conditions. Ask whether a value is a measurement, a classification, a statement from someone or evidence supporting a statement. Then examine the allowed values, exceptions, time dependence and cross-domain consequences.

An illustrative address review makes this concrete. The Property Pack candidate distinguishes the property from an address and relates them through a property-to-address relationship. A reviewer could provide a fictional case in which one property is described differently in a marketing record and a title record. The question is whether the candidate can express the relevant distinction without merging the property with either description. This is evidence for examining a model; it is not an instruction to add an unapproved term.

Conditional questions need similar care. The retained 451-item validation report finds 283 selected rows with requiredness conditions. A source field's absence may be appropriate because its condition does not apply. A different case may require a value that has not been supplied. Treating both cases as the answer No would lose meaning. A reviewer should describe the condition and provide contrasting examples, rather than merely request that the field become optional.

## Write feedback that another person can act on

The participant guide's review pattern is deliberately concrete: identify the affected term, page or artefact version; describe the problem and its practical consequence; supply evidence or a counterexample; suggest a change if possible; and indicate whether other contexts may be affected. This supports review even when the contributor cannot name the eventual ontology construct.

For example: “In candidate version X, this definition appears to describe the instruction date, but our source distinguishes instruction from inspection. The attached fictional case has different dates. Please check whether the proposed property preserves that distinction.” This is more useful than “the dates are wrong,” because it identifies a testable interpretation. The example is a feedback technique, not a claim that this defect exists in the current candidate.

A proposed merge also needs evidence. Similar labels are insufficient: two concepts can have different identity criteria, obligations or time behaviour. Conversely, two source paths may express the same reviewed concept. Keep source-path coverage and semantic consolidation separate so that neither repeated names nor an attractive reduction in counts determines the answer.

## Follow the contribution through a human disposition

The domain or scheme group reviews its meaning; Interoperability handles shared boundaries and mappings with affected owners; technical reviewers assess implementation consequences. AI can organise material and propose candidates, but it does not supply the human determination. A discussion comment is not a vote or an accepted decision simply because nobody replies.

The useful end state is a traceable disposition: the contribution was incorporated in a named version, retained as unresolved evidence, rejected with reasons, or referred to the appropriate owner. Proposed lifecycle and workflow records describe further process detail but do not create operative thresholds merely by being documented. A contributor should be able to see what happened to the question and which evidence supported the outcome.
