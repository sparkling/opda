# Ontology-first change and a controlled migration

For technical reviewers, model owners and implementers.

The accepted direction in ADR-0039 is to develop SPDTF around governed linked-data meaning and use that model to drive downstream artefacts. A semantic change could then be reflected in documentation, validation profiles and familiar exchange formats through explicit transformations. This direction is different from a claim that every generator exists, that a new schema is already approved, or that existing implementations can switch automatically.

Proposed ADR-0091, dated 11 October 2026, describes a practical transition from the existing schema-first pull-request process to an ontology-first change process. It calls for a worked demonstration, technical-subgroup ownership and a separately agreed compatibility and cutover approach. It remains Proposed. Existing pull requests are not approved by being used as examples, and existing handling remains in place until an authorised transition decision changes it.

## Begin with the change being requested

A schema pull request may appear to add a field, change an enumeration or alter requiredness. The semantic investigation asks what real-world distinction or business rule motivates the change. Is a new concept needed? Is the value an attribute of an existing resource or evidence about an observation? Does it belong in the stated context? Does another group consume it, and would the change alter their interpretation?

Consider an illustrative request to replace a yes/no value with Yes, No and Unknown. This is not merely a larger enum. It changes what the exchange can say, how a missing value should be interpreted and possibly how existing consumers make decisions. A receiver that currently treats every value other than Yes as No would silently lose the new distinction. The change requires examples and compatibility analysis before a generated schema can be considered a safe replacement.

Another request might change a property identifier from a numeric representation to digit-preserving text. The modeller must establish whether arithmetic is meaningful, whether leading zeroes matter and what the source's identifier rules require. A transformation can convert syntax while still losing identity information. Data-type similarity is therefore not a substitute for an explicit meaning-preservation claim.

## From reviewed meaning to a draft delivery profile

The proposed workflow follows the source request through semantic impact, an ontology proposal, human review, draft schema generation, validation, independent approval and versioned release. These are separate artefacts and decisions. A demonstration should make their boundaries visible so that the process can be operated by the responsible subgroup rather than depend on one modeller.

SHACL shapes are an important bridge because they state selected graph constraints: cardinality, datatype, allowed values, node kind and relationships. OWL and RDFS describe semantic relationships and entailments; they do not by themselves supply every document-validation rule. For example, an RDFS domain statement can support type inference. It should not be taught as a rule that rejects every use of a predicate outside a class.

A target such as JSON Schema has its own representation choices. A graph relationship may become a nested object, an identifier reference or another explicitly defined structure. A graph can describe shared resources referenced from several places; a tree-shaped message may need rules for duplication or reference resolution. The generator needs a documented contract for these choices, and any unrepresented constraints need additional checking or an explicit limitation.

## Compare actual versions, not attractive diagrams

ADR-0091 identifies a concrete comparison between modular PDTF schemas and ontology-derived outputs. The useful evidence is a versioned difference: structure, semantic coverage, value restrictions, cardinalities, mappings and representative instances. Comparing only a field count misses changes in scope or interpretation. Comparing only a successful example misses the invalid or exceptional cases that reveal incompatible rules.

The 451-item Property Pack boundary illustrates the required care. Many source rows are conditionally required. Turning every such row into an unconditional required field would reject legitimate cases. Conversely, omitting every condition would accept records that lack information when the condition applies. Array traversal introduces another distinction: a leaf's cardinality within one parent is not necessarily the cardinality of the collection of parents.

Historical round-trip demonstrations are useful but bounded. The schema-derived programme proved particular mappings and BASPI5 cases. Accepted ADR-0066 withdrew full-schema round-trip as the greenfield Property Pack acceptance condition. A previous mapping therefore cannot be cited as proof that the new candidate is equivalent to the entire legacy schema. Each relevant compatibility proposition needs its own evidence.

## Migration is also a consumer decision

The technology team must decide which compatibility obligations matter, whether adapters are needed, whether versions coexist, how deprecation is signalled and who owns release. ADR-0091 does not settle the duration of a transition or promise a painless cutover. Those decisions depend on actual consumers, their data and their operating constraints.

An adapter may preserve an old payload while translating it into a new representation. That helps a consumer adopt incrementally, but it can also conceal information loss if the new model carries distinctions the old payload cannot express. The adapter should therefore identify unsupported states and preserve the source version. A clear limitation is safer than manufacturing a value to make every record appear conformant.

Consumers also need to know what remains stable: an identifier, a concept's meaning, a validation profile or merely a web address. Documentation routes can move without changing canonical identifiers. Conversely, a stable-looking label may conceal a significant semantic change unless version and decision records make it explicit.

## An accepted direction with an honest implementation boundary

The repository's model-driven generation account distinguishes built, partial and planned capabilities. Generated documentation and historical mapping demonstrations provide real evidence. Broader generation of API contracts, code, database definitions and interfaces is a roadmap, not a universal service already delivered by the candidate. A governed ontology supplies meaning; tested generators and target-specific decisions turn that meaning into usable outputs.

An ontology-first process earns confidence when a concrete change can be followed from its original request through a human decision, a reproducible transformation and observed consumer consequences. The proposal's purpose is to make those responsibilities repeatable. It does not replace review with generation, or migration judgement with a successful build.
