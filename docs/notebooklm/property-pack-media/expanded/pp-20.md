# Time, state and the history of property information

For property professionals, data stewards and implementers.

A date in a property record can mean when an event occurred, when a statement was valid, when a document was issued or when software recorded it. Treating all these as “last updated” makes it difficult to answer a simple question: what did we know at the time a decision was made?

The accepted OPDA temporal method, ODR0053, distinguishes valid time from recorded time and preserves change through immutable transition records. Its companion provenance method, ODR0052, explains extraction and generation history. Both are accepted modelling methods with implementation pending. They provide a precise way to discuss requirements; they do not establish that the current Property Pack candidate already offers a complete historical query service.

## Different dates answer different questions

Consider an illustrative planning decision effective on Monday, entered into a provider's system on Wednesday and obtained by a conveyancer on Thursday. Monday concerns the domain fact. Wednesday concerns when the record was made. Thursday concerns when another participant acquired it. A later extraction may introduce a fourth time without changing any of the earlier ones.

Someone asking what applied on Tuesday needs a different answer from someone asking what the provider had recorded by Tuesday. Someone examining the conveyancer's decision needs to know what information was available to that participant. Keeping these questions distinct supports fair investigation of delayed information and later corrections.

The actual Property Pack source workbook already contains several kinds of date-bearing information. Listed-building consent-order entries distinguish application date, application type, description, proposal status and reference. Lease entries distinguish lease date and lease term. These fields motivate careful temporal interpretation, but their existence does not supply a complete meaning or validation rule. The evidence-validation report specifically identifies a lease-date field lacking a date format in the historical schema.

## A transition is more than a replacement value

If a system stores only the latest state, replacing “pending” with “decided” destroys the earlier value unless another record preserves it. ODR0053 instead describes an immutable transition entity identifying the subject, its previous state, its new state and an effective instant. A generation timestamp can record when that transition entity was created, and a provenance link can identify the activity that recorded it.

This separates the domain change from the act of recording it. The method places `prov:generatedAtTime` on the transition entity; the recording activity has its own start and end times. These choices avoid an ambiguous timestamp whose subject changes according to the reader's assumptions.

The “pending” and “decided” example is illustrative, not an adopted OPDA state vocabulary. A real state space needs governed definitions, appropriate members and the responsible domain's agreement about what each transition means. A generic label cannot establish that two different organisations use the same process or decision boundary.

## State categories and permitted movement

A taxonomy groups concepts by meaning. It does not necessarily describe the order in which events can happen. ODR0053 therefore keeps a state-space concept scheme separate from the relationship expressing allowed one-step successors. SKOS broader and narrower relationships retain their meaning as conceptual hierarchy; they are not used as an improvised state machine.

For an illustrative inspection record, “awaiting inspection” and “inspection completed” might be distinct states. Whether a completed inspection can be reopened is a process question requiring evidence, not something deduced from the words' positions in a taxonomy. The temporal method requires prior and new states to be distinct and belong to the same typed state space, but it does not invent the business rules for every property activity.

This helps separate two kinds of error. A malformed transition may omit the subject or effective time. A perfectly structured transition may still describe an unauthorised or impossible business change. Structural validation can detect the former. The latter needs the applicable process rules and evidence about what actually occurred.

## Instants, intervals and useful boundaries

The method adopts a bounded set of OWL-Time terms for instants and intervals, with relationships such as before, after, during and meets. It does not import the entire temporal vocabulary by default. A proper interval needs a beginning and an end later than its beginning; instants use the selected timestamp datatype.

An illustrative certificate-validity interval and an extraction timestamp therefore serve different purposes. The interval expresses when a certificate is represented as valid in the relevant model. The extraction timestamp describes a processing event. Re-extracting a document today cannot make its substantive evidence newly current. Equally, an old extraction is not automatically wrong if the underlying information remains applicable.

Some time values are ordinary domain information rather than state transitions. A lease term, a period mentioned in a seller's answer and the date of an application each need their own definition. The temporal method explicitly keeps domain change, extraction provenance and calendar-period data distinguishable. It does not require every date to become an event in one universal workflow.

## Snapshots and history

A snapshot can be a useful view of a subject at an instant: it makes a historical question easier to answer without replaying every change in the user interface. ODR0053 treats such snapshots as optional computed views. The transition chain remains primary, and snapshot versions can have explicit supersession relationships.

That arrangement creates a practical trade-off. A snapshot improves convenience, but its date and derivation must be clear. Otherwise a copied view can appear to be a fresh authoritative record. Maintaining transitions preserves the basis for rebuilding a view and investigating a correction. A system should not create snapshots simply because the pattern permits them if the underlying query already answers the need.

The method also defers broader overlapping-interval consistency rules. It would be misleading to describe an accepted temporal design as a delivered validator that detects every contradiction. A concrete use case must establish which conflicts matter and which checks have actually been implemented.

## Corrections and decisions made with earlier knowledge

Suppose a supplied record is corrected after an offer has been made. A useful history preserves the previous record, the corrected information, the relevant effective times and when the correction became known. Provenance identifies the source and activity behind the revision. This allows participants to explain why earlier decisions differed without pretending the latest view was always available.

The DPMSG trust-framework explainer's emphasis on timestamps, versions and validity makes this an operating concern as well as a modelling concern. Reusing information safely requires knowing which version and time boundary a recipient is relying on. The practical result is a more precise question than “is this data up to date?”: current for which subject, which purpose and which moment, according to which source?
